# 客户攻单AI — 产品路线图

> 制定日期:2026-09-29
> 基线版本:v0.7.0
> 规划范围:v0.8 → v1.0

## 1. 现状判断

v0.7.0 已完成功能闭环:客户录入 → 类型判断 → 会前简报 → 会中辅助 → 会后跟进 → 外部背调,LLM 已全量接入并保留规则引擎降级。但从 demo 到销售团队"每天都在用",存在三个关键断点:

1. **知识飞轮没有转起来(最致命)。** 状态机设计了"复盘优化 → 知识库更新",但 `followup_service.py` 只产出 `knowledge_update_suggestion` 文本,没有任何审核入库流程,建议生成后靠人肉复制粘贴。知识库不增长,简报和话术的质量天花板就是初始化时的种子数据,用得越久越显得千篇一律,这是 AI 销售工具被弃用的头号原因。
2. **现场场景不成立。** 开发原则明确"现场可用优先",但会中辅助要求销售在拜访现场打字输入客户原话,这不现实。README 待实现清单里的"实时语音转写"正是为此,它是产品价值兑现的钥匙,不是锦上添花。
3. **无法团队化。** `init_db.py` 硬编码 admin/admin123、sales/sales123 两个账号,没有用户管理。真实团队(1 个主管 + N 个销售)无法上线,owner 隔离机制等于空转。

## 2. 版本规划

### 2.1 v0.8「知识飞轮」— 让系统越用越准(约 2~3 周)

> ✅ **已实现(2026-09-29)**:四项全部交付——建议审核流(`POST /api/v1/knowledge/suggestions/{id}/approve|reject` + 知识库后台 UI)、来源卡反馈(`POST /api/v1/feedback` + 看板采纳率)、LLM 调用观测(`llm_call_logs` + 看板近7天视图)、混合检索(FTS5+embedding RRF 融合,`scripts/eval_retrieval.py` 可量化对比)。99 个 pytest + 前端冒烟 + GUI 走查通过。

**主题:把闭环的最后一环焊上,让输出质量随使用提升。**

| 事项 | 说明 | 验收标准 |
|---|---|---|
| 知识更新建议审核流 | 跟进包中的建议变成结构化草稿,admin 在知识库页面一键审核/编辑/入库 | 建议从产出到入库 ≤ 3 次点击,入库后下次简报可命中 |
| 来源卡反馈(采纳/无效) | 会中辅助、简报的每条建议支持采纳/无效反馈并落库 | 有反馈数据表,看板可见采纳率 |
| 混合检索升级 | 在 FTS5 之上叠加 embedding 向量检索(列已预留),召回排序融合 | 建立简报/辅助相关性评测集,命中率提升可量化 |
| LLM 用量与降级可观测 | 记录每次 LLM 调用的 token/耗时/降级原因 | 看板新增 LLM 用量视图,降级可及时发现 |

**优先级依据:** 不需要新能力,全是把已有产物串起来;成本最低,且直接决定后面语音场景"接进来的是好建议还是废话"。采纳率数据也是后续所有迭代的决策依据。

### 2.2 v0.9「现场可用」— 兑现核心场景(约 3~4 周)

> ✅ **已实现(2026-09-29)**:实时辅助模式(语音转写→停顿自动生成建议,含异常优雅降级)、PWA(manifest+SW+图标,可安装)、移动端适配(弹窗近全屏/44px 触控/防 iOS 缩放)、离线兜底(简报/建议 localStorage 缓存+离线徽标)。语音识别采用浏览器 Web Speech API 方案,后端 ASR 留作后续增强项。

**主题:销售在拜访现场真的用得起来。**

| 事项 | 说明 | 验收标准 |
|---|---|---|
| 会中实时语音转写 | 浏览器 Web Speech API 或后端接 ASR(Whisper/云厂商),转写文本实时喂给现有 assist 链路 | 现场说一段客户异议,10 秒内出现话术建议且带来源 |
| 移动端适配 / PWA | 现有原生 HTML/JS 单页应用改造为移动优先 + 可安装 | 手机上完成"打开 → 会中辅助 → 拿到建议"全流程 |
| 会中阶段自动识别 | 基于转写流识别当前处于需求挖掘/方案/报价/异议阶段,按阶段检索话术(工作流设计已规划,未实现) | 阶段切换无需手动,检索命中率对比现状提升 |
| 离线兜底 | 现场网络不稳时的降级策略(缓存客户简报到本地) | 断网状态下可查看已生成的简报 |

**风险提示:** 语音识别中文销售行话准确率需要实测,建议先用真实拜访录音做离线评测集再选型。

### 2.3 v1.0「团队与集成」— 可以部署给一个团队(约 4~6 周)

> ✅ **已实现(2026-09-29)**:用户管理(admin 创建/禁用/重置,禁用即失效,登录限速+密码策略,去除硬编码账号)、团队知识共享(个人→共享进检索池,admin 聚合)、CRM webhook 推送+日志+CSV 导出、PostgreSQL 经 DATABASE_URL 直接切换+SQLite 在线备份脚本。

**主题:从单人工具变成团队系统。**

| 事项 | 说明 |
|---|---|
| 用户管理 | admin 创建/禁用销售账号、重置密码,去掉硬编码账号;配套安全加固(强密码、登录限速) |
| 团队知识共享 | owner 隔离保留,但案例/话术支持"个人 → 团队共享"标记,主管可聚合查看 |
| CRM 集成 | 工具清单里的"CRM 写入/任务创建"落地:会后跟进包一键回写 CRM、创建待办(先做 webhook/CSV 通用方案,再接具体 CRM) |
| 数据库升级选项 | SQLite → PostgreSQL 可切换,支持备份策略 |

## 3. 指标体系

- **北极星指标:** 周活跃销售在真实拜访中使用"会中辅助"的人均次数(衡量是否真被用起来)
- **质量指标:** 建议采纳率(采纳/总反馈)、简报知识命中率、知识库月净新增条数(飞轮转速)
- **可靠性指标:** LLM 降级触发率、会中建议响应耗时 P95

## 4. 明确暂不做(及理由)

- **多端同步** — PWA + 账号体系天然解决大半,单独立项性价比低
- **后台大报表** — 与"现场可用优先"原则相悖,等采纳率数据积累后再议
- **通用 Agent 化/复杂编排** — 当前"规则+检索+生成"链路尚未被数据证明不足,先别加复杂度

## 5. 关键依赖与决策点

1. **embedding 服务选型(v0.8 前置):** 当前 LLM 配置为 OpenAI 兼容接口,embedding 走同一底座即可,但需先建中文评测集(可用 seed_knowledge 数据 + 人工标注 50 条)。
2. **语音方案选型(v0.8 期间拍板):** 自建(Whisper)还是云 API,取决于拜访录音敏感度和成本;建议用 10 段真实录音做离线对比后决定。
3. **CRM 集成目标(v0.9 期间确认):** 第一个试点团队用哪家 CRM,决定先做 webhook 还是直连。

## 6. 一句话总结

v0.7 解决了"能不能",接下来三期分别解决:**越用越准(飞轮)、真用得起来(语音+移动)、能部署给团队(账号+CRM)**。优先级唯一依据是项目自己的原则——现场可用优先、知识可追溯。
