# Gongdan AI Agent 下一阶段迭代规划

**版本：** 2026-08-16  
**适用项目：** Gongdan AI | Fenous Sales Combat Station  
**规划原则：** 先把一次诊断变成可执行的下一次动作，再逐步扩大到竞品分析、团队协作与跨设备沉淀。

## 一、现状判断与迭代目标

当前产品已经完成“客户诊断 → 七大类型判断 → 攻单助手 → 异议处理 → 客户记录 → 跟进待办”的基本闭环。客户诊断覆盖品牌、行业、规模、老板关键词、竞争状态、拜访目标和补充背景，并支持单选、多选与手动输入；诊断服务端通过结构化 JSON 输出生成主次类型、判断依据、五步法、话术、异议和下一步动作。[1] [2]

当前最重要的产品缺口不是继续增加更多话术，而是让**拜访后的真实反馈更有效地反哺下一次攻单**。现有记录保存在浏览器本地，已经有推进状态、下次跟进日期、拜访反馈和异议处理结果；但反馈摘要仍然是确定性的拼接文本，导入也还缺少预览和撤销，案例库尚未具备行业、区域和竞品标签。[3] [4]

因此，下一阶段的核心目标定义为：

> **让销售在 3 分钟内完成一次复盘，在 1 分钟内得到下一次跟进话术、行动清单和可发送的微信消息，并且不会因为导入、提醒或 AI 生成而丢失客户上下文。**

## 二、推荐的产品路线

| 优先级 | 功能方向 | 解决的问题 | 推荐程度 | 预计复杂度 |
|---|---|---|---|---|
| P0 | 类型契约修复与回归基线 | 消除 `Home.tsx` 中 `brandName` 类型风险，避免新功能建立在不稳定代码上 | 必做 | 低 |
| P1 | 拜访复盘与下一次攻单生成器 | 反馈目前只能形成简单提示，无法直接指导下一次沟通 | 首批实现 | 中 |
| P1 | 微信/短信跟进消息生成 | 策略已经生成，但销售还需要手工改写成可发送消息 | 首批实现 | 中 |
| P1 | 记录导入预览、冲突处理与撤销 | 团队迁移存在误导入、覆盖和无法恢复风险 | 首批实现 | 中 |
| P1 | 跟进日历导出与浏览器提醒 | 待办已经可见，但还没有进入销售日常工作流 | 首批实现 | 低—中 |
| P2 | 竞品深度分析与对比战卡 | 当前竞争状态只有诊断标签，缺少具体竞品拆解 | 第二批 | 中—高 |
| P2 | 行业/区域/阶段化案例匹配 | 当前案例主要按七大类型匹配，行业和区域适配度不足 | 第二批 | 中 |
| P3 | 可选云端同步与团队协作 | 本地记录无法跨设备，也无法形成团队共享资产 | 第三批 | 高 |

建议不要同时启动 P2 和 P3。第一阶段应集中在“反馈 → 复盘 → 下一次动作”的销售价值链上，因为它直接承接已有模块，数据改造较小，也最容易通过真实销售使用验证。

## 三、第一批：复盘驱动的下一次攻单

### 3.1 拜访复盘向导

在“我的记录”中增加“完成本次拜访”入口。销售不需要填写长篇纪要，而是按四步快速完成：本次结果、客户新反馈、未解决异议、下一次推进目标。每一步都允许预设选项和自由补充，以延续客户诊断中的低输入负担设计。

建议字段如下：

| 字段 | 类型 | 示例 | 用途 |
|---|---|---|---|
| meetingResult | 单选 | 有明确意向 / 继续评估 / 暂缓 / 失联 | 判断推进阶段 |
| newSignals | 多选 + 文本 | 预算、老板态度、竞品动作、内部汇报 | 更新客户判断 |
| visitFeedback | 文本 | 客户认可品牌建设，但担心预算周期 | 保留原始事实 |
| objectionOutcome | 文本 | 解决了价格异议，仍卡在老板决策 | 形成异议状态 |
| nextGoal | 单选 + 文本 | 约老板复盘 / 确认试点城市 / 补充方案 | 生成下一步动作 |
| nextFollowUpDate | 日期 | 2026-08-22 | 与现有待办兼容 |

复盘完成后，页面应同时展示三层结果。第一层是**事实摘要**，只复述销售输入，不加入模型猜测；第二层是**攻单判断**，说明客户主类型是否需要调整、当前最大阻力是什么；第三层是**下一次作战卡**，包含目标、关键人、建议切入、不要做的事、准备材料和建议话术。

### 3.2 AI 下一次攻单提示

新增服务端结构化接口 `gongdan.recap`，输入为现有客户诊断、Playbook、拜访反馈、异议结果和下一次目标，输出固定 JSON，不直接返回不可控长文本。建议输出契约如下：

```ts
interface RecapResult {
  factualSummary: string;
  customerChange: string;
  currentBarrier: string;
  confidence: "高" | "中" | "低";
  nextObjective: string;
  keyQuestions: string[];
  recommendedActions: string[];
  avoidActions: string[];
  materialsToPrepare: string[];
  followUpMessage: string;
  alternativeMessages: string[];
}
```

模型只允许使用销售输入、已有诊断和内置知识库，不得补写客户没有提供的预算、营收、竞品投放数据或决策人信息。对于缺失字段，返回“待确认”而不是生成看似确定的结论。此接口适合继续使用服务端 `invokeLLM` 与严格 JSON Schema；轻量复盘可使用 `gpt-5-mini`，复杂竞品和多轮判断再考虑更强模型。[5] [6]

### 3.3 微信跟进消息生成

在复盘结果中提供三种消息风格，而不是只生成一段万能文案：

| 风格 | 适用场景 | 内容结构 |
|---|---|---|
| 关系维护型 | 客户尚未形成明确意向 | 感谢交流 + 准确复述客户关注点 + 轻量后续动作 |
| 专业推进型 | 客户已经认可方向但需要内部评估 | 客户处境总结 + 一条案例/方法依据 + 明确资料或会议动作 |
| 决策确认型 | 已接近试点或方案确认 | 已达成共识 + 待确认事项 + 时间和责任人 |

每种消息应有复制按钮、字数提示和“重新生成”入口。产品必须将**事实性内容**与**建议性表达**区分展示，避免销售把 AI 推测误发给客户。默认消息不应包含未经输入的折扣承诺、效果保证或案例数字。

## 四、第一批：数据安全与跟进可达性

### 4.1 导入预览、冲突处理与撤销

现有 JSON 导入已按记录 ID 合并，但缺少导入前预览。[3] 下一版应改为两阶段流程：先解析文件并显示统计，再由销售确认导入。

预览页至少显示有效记录数、无效记录数、新增记录数、冲突记录数和字段缺失提示。冲突记录提供三种策略：导入覆盖本地、保留本地、逐条比较。确认导入前保存一次本地快照，提供“撤销本次导入”按钮；撤销只恢复导入前状态，不影响之后新建的客户记录。

建议将导出版本升级为 `2`，保留对 `version: 1` 的兼容读取，并在导入时执行字段归一化。任何未知字段应忽略而不是导致整个文件失败。这个设计可以继续保持免登录和 local-first，不需要立即引入数据库。

### 4.2 日历导出与浏览器提醒

第一阶段推荐先做 `.ics` 日历文件导出，而不是直接接入某个第三方日历。每条客户记录可以导出一个事件，事件标题包含品牌名称和下一步目标，描述包含客户类型、当前阻力、建议动作和跟进消息。批量导出则生成一个包含所有未完成跟进的日历文件。

浏览器通知作为可选增强：用户主动授权后，在打开网站期间提示逾期和今日待办；未授权时继续显示站内待办，不影响核心功能。由于浏览器本地存储和权限策略无法保证网站关闭后始终触达，不能把浏览器通知描述为可靠的后台提醒。若未来要求邮件、企业微信或飞书等外部渠道，应先确认连接器、授权和长期运行方式，再单独做集成评估。[7]

## 五、第二批：从“竞争状态”升级为“竞品作战”

### 5.1 竞品输入增强

当前诊断中的“竞争状态”主要是标签化线索，知识库也没有竞品名称、行业标签、区域标签和渠道维度。[4] 下一版可在诊断或复盘中增加可选的竞品字段：竞品名称、客户认为的竞品优势、竞品近期动作、客户最担心被比较的指标、希望赢下的比较场景。

AI 输出不应回答“竞品真实投放了多少”，而应生成一张**竞争假设卡**：

| 模块 | 输出内容 |
|---|---|
| 客户视角 | 客户认为自己与竞品差异在哪里 |
| 未验证事实 | 哪些信息需要销售继续求证 |
| 比较维度 | 品类心智、品牌资产、核心城市、渠道承接、决策风险等 |
| 攻单切入 | 应该先比什么，不应该先比什么 |
| 追问问题 | 下一次拜访需要确认的 3—5 个问题 |
| 证据需求 | 需要准备的案例、客户数据或内部材料 |

这能避免把“竞品分析”做成没有证据的排名，同时让五步法中的“比”更贴近具体客户。

### 5.2 行业、区域与阶段化案例匹配

案例库目前仅有 `id`、`name`、`type`、`summary`、`metric` 和 `fit` 等字段，匹配函数主要按主类型和次类型筛选。[4] 建议逐步给案例增加 `industryTags`、`regionTags`、`businessStage`、`channelTags`、`evidenceLevel` 和 `sourceNote`。

匹配结果从“案例名称数组”升级为带分数和理由的对象：

```ts
interface CaseMatch {
  caseId: string;
  score: number;
  reasons: string[];
  cautions: string[];
}
```

程序化匹配负责标签、类型和阶段的可解释筛选；模型只负责将匹配结果翻译成销售语言。所有案例数字继续来自知识库原文，并标注“文档案例数据”，不能由模型补齐或外推。

## 六、第三批：可选云端同步与团队协作

云端同步不应破坏“不登录即可使用”的产品承诺。建议采用双层模式：匿名用户继续使用 localStorage；只有主动点击“跨设备同步”时，才进入登录和云端空间。登录后将本地记录先做差异预览，再上传到个人空间；团队空间另设成员、角色和客户记录可见范围。

建议的最小数据模型包括 `deal_sessions`、`deal_events`、`team_workspaces`、`workspace_members` 和 `record_shares`。其中 `deal_events` 用于保存诊断、复盘、异议处理和状态变化的时间线，避免只保留最后一版文本。云端化之前必须先完成权限边界、删除策略、导出策略和敏感客户信息提示，否则不宜直接开放团队共享。

## 七、技术实施拆解

| 层级 | 第一批改造 | 第二批改造 | 第三批改造 |
|---|---|---|---|
| 共享类型 | `RecapResult`、复盘字段、记录版本 2 | `CompetitorBrief`、`CaseMatch`、案例标签 | 云端记录、事件和权限类型 |
| 前端 | 复盘向导、消息卡片、导入预览、ICS 下载 | 竞品战卡、案例筛选和匹配理由 | 登录入口、同步冲突页、团队空间 |
| tRPC | `gongdan.recap`，必要时 `gongdan.generateFollowUpMessage` | `gongdan.competitorAnalysis`、增强 `knowledge` | `sync.push`、`sync.pull`、权限接口 |
| 知识库 | 复盘输出规则和消息边界 | 行业/区域/阶段标签与真实案例 | 团队可维护知识版本 |
| 存储 | 继续 localStorage，增加快照 | 继续 localStorage | Drizzle/MySQL/TiDB 为主，localStorage 为离线缓存 |
| 测试 | Vitest 契约、导入撤销、时区和消息事实边界 | 匹配分数、无证据竞品声明拦截 | 权限、冲突合并、删除和导出 |

实施顺序应是先修复 `FormState`、`CustomerProfileInput` 和 `buildCustomerProfile` 的类型契约，再新增共享类型和纯函数测试，最后接入 AI tRPC。所有模型调用必须在服务端完成，前端不能接触服务端密钥；结构化输出必须使用严格 JSON Schema，并对空内容、解析失败、超长输入和模型拒答做可见错误处理。[2] [5]

## 八、风险与控制措施

| 风险 | 具体表现 | 控制措施 |
|---|---|---|
| AI 幻觉 | 把未提供的预算、效果或竞品数据写成事实 | 事实摘要与建议分栏；严格 Schema；缺失信息标记“待确认” |
| 上下文漂移 | 复盘后主类型被随意改写，导致话术前后不一致 | 输出类型变化及理由；默认保留原诊断，允许人工确认后更新 |
| 数据误导入 | 团队迁移覆盖本地重要记录 | 预览、冲突策略、本地快照和撤销 |
| 隐私泄露 | 客户名称、预算和内部判断被发送到不明服务 | 只调用平台内置服务；界面提示输入边界；云同步前明确授权 |
| 提醒不可靠 | 浏览器关闭后用户未收到通知 | 将站内待办作为主路径，ICS 作为跨日历路径，不承诺后台通知 |
| 成本和延迟 | 每次复盘都调用高成本模型 | 默认轻量模型；短上下文；只有竞品深度分析升级模型；缓存可复用结果 |
| 案例失真 | 模型将案例数字扩写成普遍规律 | 案例数字只从知识库读取，保留来源说明和适用条件 |

## 九、验收标准与产品指标

第一批发布前，必须满足以下功能验收：销售可以从一条已有记录进入复盘，在不重新填写客户诊断的情况下生成结构化的下一次作战卡；作战卡至少包含事实摘要、当前阻力、三个追问问题、三个行动建议和一条可复制跟进消息；复盘结果能够写回记录并在下次打开记录时复现。

导入功能必须在真正写入 localStorage 前展示新增、冲突和无效数量；用户可以选择冲突策略并成功撤销最近一次导入；版本 1 JSON 能继续导入。日历功能必须生成合法 `.ics` 文件，标题、日期、描述和时区字段可被常见日历应用解析。所有新增 tRPC 输入都必须拒绝超长内容和无效枚举，AI 返回格式异常时页面必须提供可理解的重试反馈。

建议跟踪以下产品指标，而不是只看 AI 输出长度：

| 指标 | 第一阶段目标 |
|---|---|
| 诊断完成后进入复盘的客户记录比例 | 建立基线后持续提升 |
| 复盘完成率 | ≥ 70% 的开始复盘记录完成提交 |
| 复盘到下一步动作的转化率 | ≥ 80% 的有效复盘包含明确动作和日期 |
| AI 消息复制或编辑后使用比例 | 建立基线，重点观察真实使用反馈 |
| 导入撤销成功率 | 100% 的最近一次导入可撤销 |
| AI 结构化失败率 | < 2%，失败时可重试 |
| 无证据事实被采纳的反馈 | 目标为 0，发现即修复提示和知识库规则 |

## 十、建议的开发节奏

**第 1 周：基线与数据契约。** 修复类型错误，补齐 `RecapResult`、记录版本 2 和复盘字段，建立纯函数测试、JSON 迁移测试与时区测试。此阶段不增加新的模型调用。

**第 2—3 周：复盘向导与 AI 作战卡。** 完成 `gongdan.recap`、复盘 UI、结果回写和记录详情展示。优先使用已有诊断上下文，不重新要求销售输入已经存在的信息。

**第 4 周：跟进消息与导入安全。** 增加三种消息风格、复制与重生成；完成导入预览、冲突策略、快照和撤销，并验证旧版本 JSON 兼容性。

**第 5 周：日历与真实使用验证。** 完成 ICS 导出和可选浏览器提醒，邀请销售用真实但经脱敏的客户记录验证。根据反馈决定是否进入竞品战卡或案例标签建设。

**第 6—8 周：第二批能力。** 若第一批指标稳定，再做竞品输入增强、竞争假设卡和行业/区域/阶段案例匹配。云端同步保持在需求验证之后，不与第二批同时压缩交付周期。

## 十一、最终建议

下一阶段不建议直接追求“更强的聊天机器人”，而应把产品定位进一步收敛为**销售复盘与下一步行动系统**。最有价值的迭代是让每一次拜访都留下结构化事实，让 AI 将事实转译成下一次问题、动作、材料和消息，同时保留人工确认权。

推荐的第一开发单元是：**P0 类型修复 + P1 拜访复盘向导 + P1 下一次攻单生成器**。完成后再接入消息生成、导入撤销和 ICS 日历。这样既延续现有免登录、本地优先和知识库约束，也为未来的竞品分析、行业案例和云端团队协作建立稳定的数据基础。
